19:T567c,<p>The bridge is a structural design pattern that helps in splitting up a complex piece of code into multiple parts so that each part can be developed, scaled and maintained independently.</p>
<p>You will commonly see this employed when you have classes in your code that have multiple tangential functionalities. In such a case, it is better practice to split the functionalities up into smaller classes and build a mechanism (<em>a bridge, maybe?</em>) to connect them</p>
<p>Let us take a look at an example to understand better</p>
<h3>Employee Management system</h3>
<p>Assume that your workplace needs an employee management system. As part of this requirement, you need to categorize your workforce by gender and their function/department.</p>
<p>Currently, you have the following genders and department:</p>
<p><strong>Genders</strong></p>
<ul>
<li>Male</li>
<li>Female</li>
</ul>
<p><strong>Department</strong></p>
<ul>
<li>Developer</li>
<li>Product manager (PM)</li>
<li>Human Resources (HR)</li>
</ul>
<p>A naive way of approaching this problem would be to implement multiple structs, like, <code>MaleDeveloper</code>, <code>FemaleDeveloper</code>, <code>MalePM</code>, <code>FemalePM</code>, and so on. This is fine if we have already defined a set of genders and departments. However, that's never realistically the case.</p>
<p>We can always grow departments to include more functions and we can always onboard employees who identify as non-binary (let's not be ignorant 🏳️‍🌈). The problem that would arise then is that, for every new gender we onboard, we would have to create 3 new structs - one for each combination of the new gender and existing departments.</p>
<p>This number would only increase as our organization grows and it's going to be a nightmare to maintain these structs 😨</p>
<blockquote>
<p>Note: Go does not have classes. Structs are a way of implementing classes in golang. If you're working with another programming language, think <code>classes</code> every time I say <code>structs</code></p>
</blockquote>
<p>Enter, the Bridge pattern. According to the Bridge pattern, we should separate the different dimensions of a struct into separate sub structs. In this case, we would have separate structs for each gender and separate structs for each department.</p>
<p>Let's take a look at this:</p>

<span data-line=""><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">func</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> (</span><span style="--shiki-light:#E36209;--shiki-dark:#FFAB70">hr </span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0">HR</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">) </span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0">getDepartmentName</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">() </span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">string</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> {</span></span>
<span data-line=""><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">    return</span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF"> "human resources"</span></span>
<span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">}</span></span></code></pre></figure>
<p>As you can see, we have successfully separated the functionalities by gender and department. Notice however, that we have a <code>department</code> key in both the gender structs. This key is, in fact, the <strong><em>bridge</em></strong> between the two dimensions, gender and department.</p>
<p>Now, every time we need to create a new gender or department, we only have to create one additional class and the bridge takes care of the rest.</p>
